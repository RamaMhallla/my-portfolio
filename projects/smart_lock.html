Secure Smart Lock: End-to-End IoT Security

IoT Security course, University of Calabria Presented February 2026 Completed

Team: Ibrahim Shkhis, Rama Mhalla, Vincenzo Damico

Course instructors: Prof. Michele Ianni, Prof. Antonio Guerrieri, Prof. Claudia Greco

Overview

A remote smart lock system built around secure communication, addressing common weaknesses in home-automation infrastructure. A Flutter app unlocks an ESP32-based lock over Bluetooth, the ESP32 exchanges data with the cloud over MQTT, and access events and gas sensor readings are logged for monitoring. The goal was for all communication to be secure end to end and resistant to replay attacks. The project extends the smart lock of my Integrated Smart Home Platform.

Security Goals

  • Authentication of users and devices
  • Integrity of every command and message
  • Confidentiality of PINs, OTPs and sensor data
  • Accounting of every access attempt
  • Authorization before the lock opens

System Architecture

The app sends the PIN to the ESP32 over Bluetooth. The ESP32 forwards access requests, emergency-open commands and gas-level data over MQTTS, and access events are stored in InfluxDB.

  • Bluetooth link: messages between the Flutter app and the ESP32 protected with AES encryption and HMAC authentication
  • Cloud link: MQTT and HTTP secured with TLS (MQTTS) using OpenSSL
  • Credential server: a custom Python Flask server handling authentication, authorization and accounting
  • Replay protection: one-time passwords and nonces validated on the server side
  • Hardening: insecure MQTT port 1883 disabled, and the ESP32 runs only as a client with no open TCP ports
  • Deployment: services containerised with Docker, with Node-RED handling the message flows

Attack Testing: Before and After

The system was attacked before and after the security measures were added, using Bettercap, Wireshark and Nmap.

Test Before security After security
Man-in-the-middle ARP spoofing intercepted traffic; PIN and OTP readable in Wireshark Traffic still intercepted, but the payload is fully encrypted and unreadable
Replay attack A captured MQTT message replayed later was accepted Replayed messages rejected by server-side OTP and nonce validation
Rogue MQTT client — Connection without valid TLS certificates rejected at the protocol level
Port scanning — Insecure port 1883 disabled and only secure ports exposed; no open TCP ports on the ESP32
